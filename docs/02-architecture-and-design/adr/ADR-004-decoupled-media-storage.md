# MetroLMS — Architecture Decision Record (ADR)
## ADR Identifier: `ADR-004` — Decoupled Enterprise Media Storage Contract

> **Document Title:** Decoupled Enterprise Media Storage and Direct Client Streaming  
> **Document Identifier:** `METROLMS-ADR-CORE-004`  
> **Document Status:** `ACCEPTED`  
> **Canonical Authority Level:** Level 2 Architecture Decision Record  
> **Target System:** MetroLMS (Cairo Metro E-Learning Platform)  
> **Prepared For:** Enterprise Architecture Review Board & Project Owner  
> **Governing Decisions:** [`D-MEDIA-01`](../../architecture/decision-register.md#d-media-01)  
> **Last Updated:** 2026-11-12 (Phase 1 Baseline Authoring)

---

## 1. Context & Problem Statement
MetroLMS delivers hundreds of hours of high-definition video lessons for technical rail training. Routing large video binary streams through the Django application server tier causes severe thread blocking, memory consumption, and network saturation, degrading core API responsiveness.

## 2. Decision Drivers
- **API Performance:** Isolation of backend workers from multi-megabyte / gigabyte video file streaming.
- **Scalability:** Ability to support 5,000 concurrent learners streaming videos simultaneously.
- **Storage Flexibility:** Decoupling storage implementation (local NAS, S3-compatible, or enterprise SAN).

## 3. Considered Options
- **Option 1: Application Server File Streaming:** Django serves video files directly via `FileResponse`.
- **Option 2: Decoupled Media Storage with Direct Client Streaming (Chosen):** Video binaries served directly from decoupled storage/delivery tier without streaming through Django WSGI.
- **Option 3: External Public Video Hosting (YouTube / Vimeo):** Unacceptable for proprietary internal safety training.

## 4. Decision Outcome
- **Chosen Option:** **Option 2 (Decoupled Media Storage with Direct Client Streaming)**.
- **Governing Authority:** Level 1 Owner Decision [`D-MEDIA-01`](../../architecture/decision-register.md#d-media-01).

## 5. Pros and Cons of the Options
### Option 2 (Decoupled Storage — Chosen)
- **Positive:** Django application servers handle only lightweight JSON API requests and session validation.
- **Positive:** Web servers / storage tier handle byte-range video streaming (HTTP 206 Partial Content) natively.
- **Negative:** Requires a separate media delivery and authorization layer (`CL-03` short-lived signed URLs `OWNER APPROVED`, `2026-11-13` as **future architectural direction; implementation deferred** — Phase 1 uses Django-mediated, session-authenticated streaming).

## 6. Implementation Notes & Consequences
- Django backend stores media metadata in SQL Server and enforces `D-AUTH-01` / `D-SEC-01` authorization.
- **Phase 1 Django-Mediated Delivery (`OWNER APPROVED`, `2026-11-13`):** During the initial production phase, MetroLMS delivers owned media through authenticated Django endpoints (`D-AUTH-01` session cookies + `D-SEC-01` authorization + Storage Abstraction, preserving HTTP `Range`, `206`, `416`, repeated Range requests, and native seeking). No separate Media Delivery Service is required in Phase 1 (and no Starlette, Uvicorn, ASP.NET Core, S3, MinIO, CDN, Redis, Celery, or silent ASGI change is introduced). Known trade-off: media transfer passes through Django infrastructure, increasing worker occupancy, bandwidth consumption, and resource pressure under concurrent video playback (throughput/capacity assumptions must not be invented and require representative workload validation).
- **Future Direct-Client Streaming & `CL-03` Signed URLs (Implementation Deferred):** `ADR-004` direct client streaming (raw video binaries bypassing Django WSGI) and `CL-03` (`OWNER APPROVED`, `2026-11-13` — short-lived signed URLs issued after Django authorization and independently validated by the delivery layer) remain preserved as the **future architectural direction** once measured traffic or operational performance justifies a separate media delivery layer.
- **Immutable Historical Binaries (`INV-DOM21-07` — `OWNER APPROVED`, `2026-11-13`):** Any media asset associated with a `PublishedCourseVersion` or sealed/closed `GroupRenewalCycle` is binary- and identity-immutable (never overwritten in place; old `assetId` never reused). Replacement creates a new asset with a new `assetId` while storage preserves the original binary independently; creating a new asset does not authorize deleting the old asset. Exact endpoint paths/DTOs/idempotency/transaction boundaries, unestablished role-to-permission mappings, metadata mutability, deletion, retention, and progress/record impact remain unresolved.
- **Active / Unsealed Group Renewal Cycle Replacement (`INV-DOM21-08` — `OWNER APPROVED`, `2026-11-13`):** Media assets associated with an Active / Unsealed `GroupRenewalCycle` are replaceable (a cycle is not immutable merely because it has started; after replacement succeeds, the active cycle uses the replacement media and the old media is no longer its active reference). If the old asset is also referenced by any protected historical content (`PublishedCourseVersion` or sealed/closed `GroupRenewalCycle`), do not overwrite globally: create a new `assetId`, update only the active cycle's reference, and preserve the old binary without auto-deletion.
- **New Asset Identity for Every Binary Replacement (`INV-DOM21-09` — `OWNER APPROVED`, `2026-11-13`):** Every binary replacement across all lifecycle states and reference counts (published versions, sealed/closed cycles, active/unsealed cycles, single active-cycle-owned assets, draft-exclusive assets, and single/multiple references) must create a new media asset with a new stable `assetId`. In-place binary overwriting and `assetId` reuse are prohibited, and `API-REC-07` `PUT`/`PATCH` metadata operations never authorize in-place binary replacement. Other references remain unchanged unless separately authorized, and creating a new asset does not authorize deleting the old asset.
- **Draft Course Version Media Replacement (`INV-DOM21-10` — `OWNER APPROVED`, `2026-11-13`):** Authorized course administrators may replace media referenced by a Draft Course Version before publication through the authorized draft editing workflow, strictly following `INV-DOM21-09` (new `assetId`; no in-place binary overwrite; leaves published versions, sealed cycles, unrelated active-cycle references, and the old binary unchanged without deleting the old asset).
- **Draft Media Replacement Authorization (`INV-DOM21-11` — `OWNER APPROVED`, `2026-11-13`):** A user may replace media associated with a Draft Course Version **only** if authorized to edit **that specific target Draft Course Version** (inherited from `domain-05` Draft Course Version editing scope under `D-SEC-01`, `INV-R6`, and `INV-R9` without inventing new roles; general upload permission alone never authorizes draft replacement or repointing; server-side enforcement is mandatory; scope is strictly Draft Course Version replacement).
- **Two-Step Media Upload & Reference Repoint Workflow (`INV-DOM21-12` — `OWNER APPROVED`, `2026-11-13`):** Approved replacement (`INV-DOM21-10` drafts, `INV-DOM21-08` active cycles; never `INV-DOM21-07` historical references) is separated into two distinct operations: **Step 1** uploads via Django `multipart/form-data`, validates context authorization and file rules, and creates a new asset (`assetId`) via Storage Abstraction **without automatically modifying any content reference**; **Step 2** separately repoints only the target reference after independently revalidating target authorization, lifecycle state, eligibility, and `assetId` validity (replacement completes only after Step 2 succeeds). Not one atomic DB transaction: if Step 1 succeeds and Step 2 fails, the old reference stays unchanged and the new asset is not auto-deleted (cleanup tracked in `B-08`). Exact endpoint paths, HTTP methods, DTOs, multipart field names, status/error codes, asset lifecycle status values, idempotency-key/retry protocol, and transaction boundaries remain `PROPOSED`.
- **Context-Specific Media Display Metadata (`INV-DOM21-13` — `OWNER APPROVED`, `2026-11-13`):** Display metadata `title` and `isVisible` belong to the specific content/material usage reference (independent per usage reference; updating one reference must not modify other references to the same Media Asset), while `fileName`, `mimeType`, and `sizeBytes` remain Asset-level technical metadata. `API-REC-07` `PATCH` operates on the applicable content/material reference (not globally on a Media Asset), while `PUT` retains file-reference/asset metadata replacement; neither authorizes in-place binary replacement.
- **Reference Metadata Mutability Follows Content Lifecycle (`INV-DOM21-14` — `OWNER APPROVED`, `2026-11-13`):** Reference-level `title` and `isVisible` mutability is governed independently by the lifecycle state of the target reference: **mutable** in Draft Course Versions and Active / Unsealed Group Renewal Cycles (subject to existing authorization), and **historically immutable** in Published Course Versions and Sealed / Closed Group Renewal Cycles (in-place `PATCH` prohibited; future versions/cycles manage their own references independently). Does not extend to Asset-level technical metadata (`fileName`, `mimeType`, `sizeBytes`).
- **Immediate Visibility Enforcement for Active Group Renewal Cycles (`INV-DOM21-15` — `OWNER APPROVED`, `2026-11-13`):** Changing `isVisible` from `true` to `false` on a material reference in an Active / Unsealed `GroupRenewalCycle` takes effect **immediately** after successful persistence for all trainees in that cycle (denying new access initiation while retaining the Media Asset and material reference, preserving all learner progress/completions/attendance/attempts/history/certificates, and isolating unrelated references). `isVisible: false -> true` restoration, already-open playback sessions / in-flight HTTP `Range` requests / previously issued media responses, technical caching/propagation mechanisms, and additional `B-13` audit/ops requirements remain unresolved.
- **Immutable Asset-Level Technical Metadata (`INV-DOM21-16` — `OWNER APPROVED`, `2026-11-13`) & `API-REC-07` Reconciliation:** Asset-level technical metadata (`fileName`, `mimeType`, `sizeBytes`) becomes **immutable immediately after asset creation** across all lifecycle states and reference counts, established from the uploaded binary and its server-side validated properties (client-declared MIME/size never authoritative without server-side validation). Binary replacement creates a new `assetId` with its own technical metadata (`INV-DOM21-09`, `INV-DOM21-12`), leaving the previous asset and its technical metadata unchanged. `INV-DOM21-16` preserves `API-REC-07` historically and supersedes any conflicting interpretation of `API-REC-07` **only** regarding post-creation mutation of `fileName`, `mimeType`, and `sizeBytes`; `PUT` must not mutate those immutable fields, and exact revised `API-REC-07` `PUT` semantics, endpoint paths, DTOs, resource-targeting behavior, and remaining historical snapshot details remain unresolved.
- **Reconciled Upload, Network & Deferral Boundaries (`2026-11-13`):** Initial binary **upload** is `OWNER APPROVED` as `Browser -> Django Backend -> Media Storage` (`multipart/form-data`) through a storage abstraction (`INV-DOM21-06`). Per `CL-02` (`OWNER APPROVED`, `2026-11-13`), authorized delivery must support both internal network and external internet (home/mobile) access over HTTPS without exposing SMB/Windows shares or physical paths. Distinct from Google Drive `Anyone with the link` external references (`domain-06`). Exact signed-URL TTL, cryptographic signing design, delivery server, storage provider, CDN, and remaining `API-REC-06` decisions remain `DEFERRED`.
