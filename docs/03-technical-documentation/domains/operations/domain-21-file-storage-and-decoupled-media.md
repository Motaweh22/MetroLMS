## 1. Domain Responsibilities & Component Boundaries

- **Frontend / Prototype Components:** `mediaStorageService.ts` (`metro_lms_media_db` IndexedDB local blob store for course media), `materialUtils.ts` (`materialBlobRegistry` session-only `Map` for group material blobs), `groupsApi.ts` & `groupHandlers.ts` (JSON metadata endpoints for `GroupMaterialFolder` and `GroupMaterialFile`), `inMemoryStore.ts`.
- **Approved Initial Upload Architecture (`OWNER APPROVED`, `2026-11-13`):**
  - **Upload Flow & Transport:** `Browser -> Django Backend -> Media Storage` using `multipart/form-data`.
  - **Django Responsibilities:** Enforce `D-AUTH-01` session-cookie + CSRF authentication, `D-SEC-01` authorization, server-side MIME/file-type and size validation, safe internal storage key generation, writes via storage abstraction, SQL Server metadata persistence, and upload audit logging.
  - **Storage Abstraction Requirement:** Business logic and API contracts MUST NOT couple to hardcoded Windows filesystem paths, specific network shares, NAS vendors, or cloud provider SDKs. Initial deployment may use dedicated space on the existing Windows Server (subject to confirmed capacity, backup, permissions, and operational safeguards) while preserving migration to a dedicated Media Server without rewriting course/group business logic or changing logical asset references.
  - **Deferred Upload Alternatives:** Direct-to-storage upload authorization and chunked/resumable uploads are not required initially (reconsidered only if future very large video uploads, unreliable connections, resumable needs, or offload volume justify them).
  - **Critical Separation (Upload vs. Delivery):** This upload approval applies to binary upload only and does NOT alter `D-MEDIA-01` / `ADR-004` direct client streaming (raw video binaries must never stream through Django WSGI workers).
- **`CL-02` Network Exposure & Deployment Direction (`OWNER APPROVED`, `2026-11-13`):**
  - Platform and authorized media delivery MUST support both Cairo Metro's internal corporate network and external internet access (home and mobile devices) securely over HTTPS with Django session/authorization enforcement.
  - Windows file shares, SMB paths, and physical storage locations MUST never be exposed directly to external trainees; `CL-02` does NOT approve public buckets, public MetroLMS binary URLs, or a CDN.
  - **Initial Physical Storage Deployment Direction (`INV-DOM21-06` — `OWNER APPROVED — INITIAL STORAGE DEPLOYMENT DIRECTION`, `2026-11-13`):** Initial production deployment uses a dedicated media storage location on the existing Windows Server hosting MetroLMS and Microsoft SQL Server, logically and operationally separated from application source/deployment directories, application logs/temp runtime files, and SQL Server data/transaction-log directories (illustrative example only: `D:\MetroLMSMedia\`; actual drive letter/path confirmed during deployment planning). A separate server is expected later for media storage/delivery (exact role, filesystem, or streaming service not yet selected). Google Drive-hosted videos are external references and are NOT stored on the Windows media volume.
  - **Mandatory Storage Abstraction Requirements:** Target architecture MUST (1) provide a consistent interface for save, retrieve, delete, and existence checks, (2) keep physical paths out of business logic and public APIs, (3) keep logical storage keys independent of physical server location, (4) support switching from local Windows storage to a separate Media Server, (5) preserve asset references and ownership relationships during migration, (6) support transfer integrity verification (e.g., checksums), and (7) never expose Windows filesystem paths or SMB shares to trainees. No specific storage framework or provider is claimed selected.
  - **Shared-Host Operational Boundaries & Risks:** Co-locating Django, SQL Server, and media on the existing Windows Server introduces shared disk capacity & I/O contention, requiring application/media/DB security separation, free-space and growth monitoring, backup/restore coordination, Django service-account file permissions, and server-unavailability recovery planning. Exact disk/volume allocation, capacity, backup technology/retention, DR design, and AV/malware scanning are NOT yet approved or verified.
- **Entity-Based Storage Organization (`OWNER-APPROVED DESIGN DIRECTION`, `2026-11-13`):** Organize MetroLMS-owned storage primarily by owning entity (Course-owned, Group-owned, User-owned where genuine use case exists, System-level where necessary, Staging/Quarantine for temporary uploads & security validation, Derivatives such as thumbnails/previews when needed), using stable internal entity IDs (never mutable names), generated Asset IDs & safe storage keys (keeping original filenames as metadata), preserving course version relationships, distinguishing group-wide vs. cycle-specific files where lifecycle requires, and avoiding duplicate physical copies of shared assets. Design direction only — NOT a frozen physical directory tree, DB schema, or retention policy.
- **Google Drive Video Sources (`OWNER APPROVED FOR GOOGLE DRIVE VIDEO SOURCES`, `2026-11-13`):** See [`domain-06-course-content-and-lessons.md`](../courses/domain-06-course-content-and-lessons.md) — uses `Anyone with the link` viewer sharing (reference/ID stored, never copied; direct-link access limitation applies outside MetroLMS until Drive permissions change; applies ONLY to Google Drive, never MetroLMS-owned storage; no OAuth/signed URLs/proxying required).
- **Phase 1 Django-Mediated Media Delivery (`OWNER APPROVED`, `2026-11-13`):**
  - **Approved Phase 1 Delivery Flow (MetroLMS-Owned Media):** (1) Trainee requests a media resource through MetroLMS frontend -> (2) Django authenticates via `D-AUTH-01` server-side session cookies -> (3) Django independently validates `D-SEC-01` authorization (course enrollment, group membership, content visibility, cycle access, etc.) -> (4) Django retrieves the file via the Storage Abstraction (private storage, stable asset IDs; direct public access to physical paths, SMB shares, or unauthenticated URLs is prohibited) -> (5) Django streams the media response to the requesting browser -> (6) Subsequent HTTP `Range` requests are likewise subject to authorization checks.
  - **Phase 1 HTTP Streaming Requirements:** Must preserve requirements for HTTP `Range` requests, `206 Partial Content`, `416` handling for invalid/unsatisfiable ranges, repeated Range requests during playback and seeking, and native browser video playback/seeking. *(Not yet implemented or verified in the production backend.)*
  - **Architecture Constraints:** No separate Media Delivery Service is required in Phase 1 (do not introduce Starlette, Uvicorn, ASP.NET Core, S3, MinIO, CDN, Redis, Celery, or silent ASGI/app-server changes as Phase 1 requirements). Storage Abstraction and stable asset identity permit future migration to a dedicated Media Server or independent delivery layer without changing core course, lesson, group, or learner business logic or frontend/API contracts.
  - **Performance & Operational Risk:** Django-mediated streaming reduces initial complexity, but media transfer passes through Django application infrastructure, increasing worker occupancy, bandwidth consumption, and resource pressure—particularly under concurrent video playback. Production throughput and worker-capacity assumptions must NOT be invented; the implementation must be validated under representative concurrent playback workloads before claiming acceptable production capacity, and performance monitoring / future migration criteria remain open unless separately approved.
- **`CL-03` Short-Lived Signed URL Strategy (`OWNER APPROVED`, `2026-11-13` — Future Phase Direction; Implementation Deferred):**
  - **Preserved Historical Decision & Clarification:** `CL-03` (short-lived signed URLs) remains historically `OWNER APPROVED` (`2026-11-13`) as a **future architectural direction**; implementation is **deferred** and NOT authorized for Phase 1. When future requirements, measured traffic, or operational performance justify a separate media delivery layer, MetroLMS may introduce Django authorization + signed URL issuance, independent signature/expiration validation, direct browser-to-media delivery, and short-lived bearer access capabilities (HTTPS mandatory; membership revocation does not immediately invalidate already-issued URLs; distinct from Google Drive `Anyone with the link` external references).
  - **Open `CL-03` Technical Details (Not Yet Approved — Do Not Invent):** (1) exact signed-URL TTL, (2) signature algorithm & cryptographic key-management strategy, (3) signing-key rotation & invalidation procedures, (4) URL scope (asset, resource, user, or other binding), (5) reuse across multiple HTTP `Range` requests, (6) token replay & leakage mitigation, (7) exact signature-validation implementation on Windows-based delivery infrastructure, (8) URL invalidation/expiry after media replacement, deletion, or access changes, (9) whether a separate authorization proxy or dedicated media service is needed, and (10) performance/operational implications for external video streaming.
- **Remaining Deferred Architecture Boundary (`API-REC-06` remains `DEFERRED`):** Signed URL implementation & the 10 open `CL-03` details above, separate Media Delivery Server / delivery implementation, physical storage provider or NAS/File Server implementation details, CDN, malware scanning policy/engine, exact production upload file-size limits, chunked/resumable upload, backup/retention policies, and immutable asset replacement/deletion lifecycle remain **strictly deferred** under `API-REC-06`.

## 2. Domain Interactions & Lifecycle Behavior

1. **Material Resource `PUT` vs. `PATCH` Semantics (`API-REC-07`) & Immutable Asset Replacement (`INV-DOM21-07` — `OWNER APPROVED`, `2026-11-13`):**
   - `PUT /api/admin/groups/:groupId/materials/files/:fileId` (`replaceMaterialFile`) accepts JSON `{ fileName, sizeBytes, mimeType }` (no binary stream in prototype) and replaces the file-reference metadata record.
   - `PATCH /api/admin/groups/:groupId/materials/files/:fileId` (`updateMaterialFile`) accepts `{ title?, isVisible? }` and updates display metadata/visibility.
   - Both HTTP methods are semantically distinct and retained on the same resource URL per `API-REC-07`. Neither `PUT` nor `PATCH` may overwrite the underlying binary content of an immutable asset (`INV-DOM21-07`). For assets associated with a `PublishedCourseVersion` or a sealed/closed `GroupRenewalCycle`, replacement MUST create a new media asset with a new stable `assetId`, preserve the original historical binary independently in storage, and keep historical published/sealed references pointing to their original asset.
   - **Active / Unsealed Group Renewal Cycle Replacement (`INV-DOM21-08` — `OWNER APPROVED`, `2026-11-13`):** `INV-DOM21-07` immutability does NOT extend to Active / Unsealed `GroupRenewalCycle`s. Authorized replacement in an active cycle is allowed (the active cycle uses the new media, the old media is no longer the active material reference for that cycle, unrelated references are not silently modified, and sealed/closed cycles remain immutable). If the old asset is also referenced by any protected historical content (`PublishedCourseVersion` or sealed/closed `GroupRenewalCycle`), Django MUST NOT overwrite the old binary globally, MUST create a replacement asset with a new stable `assetId`, MUST update only the active cycle's material reference, and MUST preserve the old asset without auto-deletion.
   - **New Asset Identity for Every Binary Replacement (`INV-DOM21-09` — `OWNER APPROVED`, `2026-11-13`):** Every binary replacement MUST create a new media asset with a new stable `assetId`; in-place binary overwriting and `assetId` reuse are **prohibited** regardless of lifecycle state or reference count (including exclusively active-cycle-owned assets and draft-exclusive assets). Replacement steps: (1) upload & validate replacement binary, (2) create new media asset, (3) assign new stable `assetId`, (4) explicitly update the applicable, authorized content reference where replacement is permitted, (5) leave other references to the previous asset unchanged unless separately authorized, and (6) never overwrite the previous asset's binary.
   - **Draft Course Version Media Replacement (`INV-DOM21-10` — `OWNER APPROVED`, `2026-11-13`) & Draft Media Replacement Authorization (`INV-DOM21-11` — `OWNER APPROVED`, `2026-11-13`):** Authorized course administrators may replace media referenced by a Draft Course Version before publication through the authorized draft editing workflow, following `INV-DOM21-09` (new `assetId`; no in-place binary overwrite; leaves `PublishedCourseVersion`s under `INV-DOM21-07`, sealed group cycles, and unrelated active-cycle references under `INV-DOM21-08` untouched; does not delete the old asset). Under `INV-DOM21-11`, a user may replace media associated with a Draft Course Version **only** if authorized to edit **that specific target Draft Course Version** (inherited from `domain-05` Draft Course Version editing scope under `D-SEC-01`, `INV-R6`, and `INV-R9`; general upload permission alone never authorizes draft replacement or repointing; Django MUST independently enforce authorization on the server across both single-step multipart and two-step upload-then-repoint workflows; scope is strictly Draft Course Version replacement, not group materials, user files, or system assets).
   - **Two-Step Media Upload & Reference Repoint Workflow (`INV-DOM21-12` — `OWNER APPROVED`, `2026-11-13`):** Media replacement (for `INV-DOM21-10` Draft Course Versions and `INV-DOM21-08` Active / Unsealed `GroupRenewalCycle`s; never modifying `INV-DOM21-07` protected historical references) is separated into two distinct operations:
     - *Step 1 (Upload & Create Asset):* Client uploads replacement binary via approved Django `multipart/form-data` upload -> Django authenticates (`D-AUTH-01`), validates authorization for the intended replacement context (`INV-DOM21-11` for drafts; existing group-level rules for active cycles; general upload permission alone insufficient), performs server-side file validation, creates a new asset with a new stable `assetId` (`INV-DOM21-09`), stores via Storage Abstraction, and returns the new asset reference. **Step 1 does NOT automatically modify any course or group material reference.**
     - *Step 2 (Repoint Content Reference):* Client submits a separate operation identifying the target content reference and new `assetId` -> Django independently authenticates and **revalidates** user authorization for that specific target, target's current lifecycle state, target's replacement eligibility, and new `assetId` validity/eligibility (never relying solely on Step 1 checks; frontend controls are not security boundaries) -> updates only that target reference. Replacement is complete **only after** Step 2 succeeds; other references to the previous asset remain unchanged unless separately authorized.
   - **Context-Specific Media Display Metadata (`INV-DOM21-13` — `OWNER APPROVED`, `2026-11-13`) & Lifecycle-Based Mutability (`INV-DOM21-14` — `OWNER APPROVED`, `2026-11-13`):** Display metadata (`title`, `isVisible`) belongs to the specific content/material usage reference, NOT as globally shared properties of the underlying Media Asset (shared assets retain independent `title` and `isVisible` per usage reference; updating one reference must not modify other references or unrelated presentations). Under `INV-DOM21-14`, mutability of reference-level `title` and `isVisible` is governed independently by the target reference's lifecycle state: **mutable** in **Draft Course Versions** (with existing authorization) and **Active / Unsealed Group Renewal Cycles** (with existing group-level authorization), and **historically immutable** in **Published Course Versions** and **Sealed / Closed Group Renewal Cycles** (in-place `PATCH` prohibited; future cycles/versions manage their own references independently). Technical metadata (`fileName`, `mimeType`, `sizeBytes`) remains Asset-level metadata and is NOT governed by these reference-level rules. Under `API-REC-07`, `PUT` retains file-reference/asset technical metadata replacement and `PATCH` updates `title` and `isVisible` **on the applicable content/material reference** subject to `INV-DOM21-14` lifecycle state; neither authorizes in-place binary replacement, and `INV-DOM21-07`–`INV-DOM21-13` remain unchanged.
   - **Immediate Visibility Enforcement for Active Group Renewal Cycles (`INV-DOM21-15` — `OWNER APPROVED`, `2026-11-13`):** When an authorized user changes reference-level `isVisible` from `true` to `false` on a material reference in an Active / Unsealed `GroupRenewalCycle`, the update takes effect **immediately** after successful persistence: all trainees in that affected cycle are denied new access initiation (independently enforced by Django on subsequent learner access decisions), while the material reference, underlying Media Asset, all learner educational records (progress, completions, attendance, attempts, completed-course history, certificates), and all unrelated references to the same asset remain preserved.
   - **Immutable Asset-Level Technical Metadata (`INV-DOM21-16` — `OWNER APPROVED`, `2026-11-13`) & Narrow `API-REC-07` Reconciliation:** Asset-level technical metadata (`fileName`, `mimeType`, `sizeBytes` per `INV-DOM21-13`) becomes **immutable immediately after asset creation**, established from the uploaded binary and its server-side validated properties (client-declared MIME type or size MUST NOT be treated as authoritative without server-side validation; `B-01`/`B-02` remain production-readiness requirements without selecting a specific validation library or algorithm). Across all lifecycle states and reference counts, these fields MUST NOT be modified in place, display metadata updates MUST NOT alter them, and binary replacement MUST create a new Media Asset with a new `assetId` (`INV-DOM21-09`, `INV-DOM21-12` Step 1 + Step 2) leaving the previous asset and its technical metadata intact. **`API-REC-07` Reconciliation:** Preserves `API-REC-07`'s historical record (`PUT` file-reference/asset metadata replacement vs. `PATCH` reference-scoped display metadata/visibility); `INV-DOM21-16` supersedes any conflicting interpretation of `API-REC-07` **only** regarding post-creation modification of `fileName`, `mimeType`, and `sizeBytes`. `PUT` must NOT mutate immutable Asset-level technical metadata after creation, and `API-REC-07` requires a narrowly scoped amendment / API Contract review to establish exact revised `PUT` semantics, endpoint paths, DTOs, and resource-targeting behavior (without inventing a new `PUT` meaning).
   - **Separate Content Reference Removal from Media Asset Deletion (`INV-DOM21-17` — `OWNER APPROVED`, `2026-11-13`):**
     - **Operation Separation:** **Content Reference Removal** (targets a specific course, lesson, or group material usage reference) and **Media Asset Deletion** (targets the underlying Media Asset) are **distinct domain operations** and MUST NOT be conflated with binary replacement (`INV-DOM21-09`), repointing (`INV-DOM21-12`), display-metadata updates (`INV-DOM21-13`), or Asset-level technical metadata mutation (`INV-DOM21-16`).
     - **Content Reference Removal Behavior:** Removing a media item from a course, lesson, or group material affects **only** that specific target reference; MUST enforce authorization and lifecycle restrictions on that target reference; MUST NOT automatically delete the underlying Media Asset; MUST NOT modify or delete other references to the same Media Asset; and MUST NOT alter the underlying binary or its Asset-level technical metadata (`fileName`, `mimeType`, `sizeBytes`).
     - **Media Asset Deletion & Reference Dependency Protection:** An underlying Media Asset MUST NOT be physically deleted while **any** content/material reference still depends on it across **all** lifecycle states — including Draft Course Versions, Published Course Versions (`INV-DOM21-07`), Active / Unsealed Group Renewal Cycles, Sealed / Closed Group Renewal Cycles (`INV-DOM21-07`), or any other applicable usage. Implementations MUST NOT ignore inactive/historical references, MUST NOT cascade-delete an asset from an individual reference removal, and MUST NOT infer immediate physical deletion eligibility when the last active reference is removed.
     - **`API-REC-07` Compatibility:** `PUT` (subject to `INV-DOM21-16` narrow reconciliation) and `PATCH` (`INV-DOM21-13`–`INV-DOM21-15`) do not perform Content Reference Removal or Media Asset Deletion; deletion endpoint semantics remain proposed/unresolved.
   - **Logical Content Reference Detachment (`INV-DOM21-18` — `OWNER APPROVED`, `2026-11-13`):**
     - **Logical Detachment Rule:** Removing a media Content Reference from a course, lesson, or group material MUST use **Logical Detachment** rather than physically deleting the reference record. The operation MUST: (1) detach the specific Content Reference from the currently active course, lesson, or group material presentation; (2) stop presenting that reference as an active material in the affected context; (3) prevent trainees from initiating new access to the material through that removed reference; (4) preserve the historical reference record and its removal history; (5) preserve the underlying Media Asset and its binary; and (6) leave unrelated references to the same Media Asset unchanged.
     - **Historical & Learner Data Preservation:** Logical detachment MUST NOT automatically delete the underlying Media Asset or binary, modify Asset-level technical metadata (`fileName`, `mimeType`, `sizeBytes`), delete other references to the same asset, reset learner progress, delete lesson completion history, delete attendance records, reset assessment attempts, delete completed-course history, or revoke/delete issued certificates.
     - **Scope & Non-Inference:** Applies only to the logical removal mechanism and preserves all lifecycle restrictions (`INV-DOM21-07` historical immutability for Published Course Versions & Sealed / Closed Group Renewal Cycles), server-side authorization, and `INV-DOM21-07`–`INV-DOM21-17`. Do NOT infer that retaining a historical record keeps the detached reference available to trainees, that logical detachment authorizes or triggers physical asset deletion eligibility, or that it terminates already-open video sessions or in-flight HTTP `Range` requests. `API-REC-07` `PUT`/`PATCH` are not approved reference-removal endpoints.
     - **Unresolved Scope (Do Not Invent):** Exact eligibility and authorization rules for detaching references in Draft Course Versions and Active / Unsealed Group Renewal Cycles (and any additional restrictions on other lifecycle states) *(context-specific authorization rule subsequently established by `INV-DOM21-19`; exact unestablished role-to-permission mappings and authorization gaps remain unresolved)*; exact logical status/state representation, if required (do NOT invent `detached`, `removed`, or `archived`); whether actor, timestamp, reason, or other audit metadata beyond existing approved audit requirements is recorded; whether a detached reference can be restored/reattached (and whether restoration reuses the same historical reference identity or creates a new one); exact API endpoint paths, HTTP methods, request/response DTOs, status codes, and error codes; behavior of already-open playback sessions and in-flight HTTP `Range` requests; Asset soft deletion vs. archival vs. later permanent deletion; zero-reference retention and deletion eligibility; retention periods; physical storage cleanup/orphan handling; reference-counting/dependency-detection mechanism; and concurrent reference-creation-vs-deletion transaction boundaries.
   - **Context-Specific Content Reference Removal Authorization (`INV-DOM21-19` — `OWNER APPROVED`, `2026-11-13`):**
     - **Context-Specific Rule:** A user may logically detach (`INV-DOM21-18`) a media Content Reference **only** when authorized to manage content within **the specific target context** containing that reference, reusing existing context-specific content-management permissions where they already cover the operation (without inventing new roles or unnecessary independent permissions):
       - *Draft Course Versions:* Permitted ONLY if authorized to edit **that specific target Draft Course Version** (`INV-DOM21-11`, `domain-05`, `D-SEC-01`, `INV-R6`, `INV-R9`). General file-upload permission or permission to edit another course/draft is insufficient.
       - *Active / Unsealed Group Renewal Cycles:* Permitted ONLY if authorized to manage content/materials of **that specific target group or cycle** under existing group-level authorization (`D-SEC-01`, `INV-R6` read-only `Superior`, `INV-R7` assigned-group scoping for `Assistant Admin`, `INV-R9` approval gating where applicable, `GroupAssistantAssignment` `materials.delete_files` / `materials.manage_folders` in `authorization-and-permissions-design.md`). General file-upload permission, broad admin status without target-group authority, or permission on another group is insufficient.
       - *Published Course Versions & Sealed / Closed Group Renewal Cycles:* Logical Detachment MUST NOT modify protected historical references (`INV-DOM21-07`; no exception for administrators or other privileged roles).
     - **Server-Side Enforcement:** Django MUST independently verify on every reference-removal request: the authenticated user's current authorization, exact target Content Reference, owning course/lesson/group/cycle context, target lifecycle state, and Logical Detachment eligibility (never relying on frontend controls or prior upload/edit/replacement checks). Preserves `INV-DOM21-07`–`INV-DOM21-18` and `API-REC-07` (`PUT`/`PATCH` are not approved Logical Detachment endpoints).
     - **Unresolved Authorization Gaps & API Scope (Do Not Invent):** Exact target-backend role-to-permission mapping where not already documented in canonical authorization sources (including whether `assistant_admin` group-material detachment requires `INV-R9` approval or whether `supervisor` has material-detachment authority), any authorization gaps in existing course/group management permissions, exact removal endpoint paths/HTTP methods/DTOs/status & error codes/resource-targeting semantics, additional audit metadata, and restoration/reattachment.

    - **Draft Media Reference Management Through `courses.edit_curriculum` (`INV-DOM21-20` — `OWNER APPROVED`, `2026-11-13`):**
      - **Approved Mapping (No New `PermissionKey`s):** Existing `courses.edit_curriculum` authorizes managing media Content References within an eligible target **Draft Course Version**: (1) adding a media Content Reference, (2) logically detaching an existing reference (`INV-DOM21-18`), (3) repointing a reference to a newly created Media Asset (`INV-DOM21-12` Step 2), and (4) updating reference-level `title` and `isVisible` (`INV-DOM21-13`, `INV-DOM21-14`).
      - **Permission Split:** `courses.upload_lectures` authorizes Step 1 binary upload & Asset creation only and **alone never authorizes** attaching, detaching, or repointing a Draft media reference; `courses.delete_lectures` remains distinct for deleting entire lecture/quiz items; `courses.edit_metadata` remains course-level metadata.
      - **Evaluation & Scope Boundaries:** Evaluated via `UserPermissionOverride`, `ROLE_CAPABILITY_CEILINGS`, `authorId === actor.id` ownership (`lecturer` requires effective grant + ownership), `INV-R1`–`INV-R8`, Visual Role Preview barriers, and `user`/`trainee` exclusion. `assistant_admin` Draft Course scope under `INV-R7` remains **unresolved**. Applies **only** to Draft Course Versions (never Published/Sealed under `INV-DOM21-07`, Active/Unsealed Group Renewal Cycles, group materials, user media, or system media); Django independently verifies target-Draft authorization on the server. API paths, HTTP methods, DTOs, status codes, idempotency, and transaction boundaries remain unresolved under `A-01`/`A-03`.
    - **Dedicated Group Media Reference Management Permission (`materials.manage_references` — `INV-DOM21-21` — `OWNER APPROVED`, `2026-11-13`):**
      - **Approved Key & Scope:** Introduces `materials.manage_references` as a distinct permission governing media Content References within an eligible, specifically assigned **Active / Unsealed Group Renewal Cycle**: (1) adding a media Content Reference, (2) logically detaching an existing reference (`INV-DOM21-18`), (3) repointing a reference to a newly created Media Asset (`INV-DOM21-12` Step 2), and (4) updating reference-level `title` and `isVisible` (`INV-DOM21-13`–`15`).
