## 6. Summary of What Was Completed

### A. T-2.3.1 — Published Course Versions & Substantive vs. Metadata Diffing (`Rule B`, `MFR-10`)
1. **Immutable Snapshot Ledger:** Implemented `PublishedCourseVersion` snapshot collection in `InMemoryStore`, recorded upon approved publication across both `executeReviewDecision` (`outcome === 'approved'`) and `approveApprovalRequest` (`courses.publish`). Pre-seeded published courses are initialized with Version 1 snapshots.
2. **Deterministic 6-Field Substantive Fingerprinting:** Implemented `computeItemSubstantiveFingerprint` utilizing a canonical, sorted key structure over strictly the 6 substantive fields: `[type, videoUrl, pdfUrl, mediaId, content, durationSeconds]` hashed via 64-bit FNV-1a. Metadata-only fields (`title`, `description`, `order`, formatted `duration` string) are strictly excluded.
3. **Substantive vs. Metadata Diffing Engine (`Rule B`):**
   - Substantive edits increment item `contentVersion` (`N -> N + 1`) and update `contentFingerprint`.
   - Metadata-only edits preserve item `contentVersion` and `contentFingerprint`.
   - Approved publication increments course `versionNumber` and snapshots the entire curriculum immutably.
4. **Active Attempt Invalidation & Sealed Attempt Preservation:**
   - Substantive item changes reset completion **only** for modified items in active, unsealed attempts (`!isAttemptSealed(attempt)`).
   - Unchanged items in the same active attempt preserve completion.
   - Sealed historical attempts (`isAttemptSealed`: explicit seal flags, `expired_incomplete` status, completed renewal cycles, archived predecessor groups) remain strictly untouched.
5. **Draft Isolation & Anti-Spoofing Hardening:**
   - Saving drafts (`saveCourseDraft`), submitting for review (`submitCourseForReview`), and staging admin edits (`saveStagedAdminEdits`) never create version snapshots or mutate learner progress.
   - Client-supplied draft metadata (`versionNumber`, `publishedAt`, `publishedBy`, `contentVersion`) is stripped before persistence.
   - Duplicate publication calls on already decided requests fail closed or no-op without creating duplicate version snapshots.
6. **Authored Regression Suite:** 15 comprehensive specifications authored in [`frontend/src/test/course-versioning-and-diffing.test.ts`](file:///d:/LMS%20MEtro%20Project/frontend/src/test/course-versioning-and-diffing.test.ts) (`WRITTEN — NOT EXECUTED — DEFERRED TO GATE B`).

### B. T-2.3.2 — Authoritative Progress Rounding & Version-Scoped Certificate Issuance (`D-12`, `D-13`, `MFR-09`, `MFR-46`)
1. **Authoritative Progress Rounding (`D-12`, `MFR-09`):**
   - Verified and enforced the canonical formula in [`frontend/src/core/domain/progress.ts`](file:///d:/LMS%20MEtro%20Project/frontend/src/core/domain/progress.ts):
     $$\text{percentage} = \min\left(\operatorname{clamp}\left(0, 100, \operatorname{round}\left(\frac{\text{completed}}{\text{total}} \times 100\right)\right), 99\right) \quad (\text{if } \text{completed} < \text{total})$$
   - Empty curricula (`totalRequiredItems === 0`) return `0%` and `isCompleted = false` (never `100%`, `NaN`, or `Infinity`). Fixed violation in `completeAttemptLessonItem`.
   - Incomplete progress is strictly capped at `99%` whenever `completedRequiredItems < totalRequiredItems` (including the critical $199 / 200 = 99.5\% \xrightarrow{} 99\%$ boundary case).
   - Strict completion gating: `isCompleted` requires `totalRequiredItems > 0 && completedRequiredItems === totalRequiredItems` evaluated against current published `contentVersion` items.
2. **Progress Reader Unification Across All 7 Reader Groups:**
   - Replaced fragmented and legacy progress calculations across all 7 reader surfaces with `computeAttemptProgress`, `getValidCompletedItemIdsForAttempt`, and `calculateTraineeProgress`:
     1. Learning Player & Details: `getAttemptProgress`, `getCourseProgress`.
     2. Mutation Paths: `recordLessonActivity`, `markLessonComplete`, `completeAttemptLessonItem`.
     3. Student Dashboard & Profile: `getMyEnrolledCourses`, `getEnrolledCoursesForUser`.
     4. Group Supervision & Metrics: `getGroupMetrics` (including `contentVersion` validation in legacy fallback).
     5. Instructor Analytics & Reports: `getCoursePerformanceReport` (gating `status = 'completed'` strictly on `isCompleted`).
     6. Admin User Transcript: `getUserTranscript` (gating `status = 'completed'` strictly on `isCompleted` and attaching certificates).
     7. Post-Publish Reconciliation: `recordPublishedCourseVersionAndReconcileAttempts`.
3. **Version-Scoped Certificate Issuance & Lifecycle (`D-13`, `MFR-46`):**
   - Defined `CertificateRecord` bound to canonical `userId`, `courseId`, `attemptId`, `attemptNumber`, `courseVersionNumber` (`courseVersion`), `certificateLabel` (`Certificate — Course Version N`), `certificateLabelAr` (`شهادة إتمام — الإصدار N`), `courseTitleSnapshot`, `traineeNameSnapshot`, `verificationCode`, and `issuedAt`.
   - Completing Version 1 issues a Version 1 certificate. Publishing Version 2 recalculates active unsealed attempts under `Rule B`, preserves the Version 1 certificate untouched, and issues a separate Version 2 certificate upon Version 2 completion, coexisting alongside Version 1.
   - Enforced strict idempotency per `(userId, courseId, attemptId, courseVersionNumber)`.
   - Guardrails: certificates are never issued on partial progress (`99%`), empty curricula, draft/unpublished courses, preview mode (`MFR-21`), or `review_only` / `keep_no_cert` access modes.
   - Retained continuation attempts (`D-07` `self:continued:${groupId}:${attemptId}`) maintain `'full'` access mode and receive certificates upon genuine completion.

## 10. Requirements or Business Rules Clarified

1. **Empty Curricula Invariant:** When `totalRequiredItems === 0`, progress percentage is unconditionally `0%` and `isCompleted` is `false`. Attempts cannot transition to `completed` and certificates cannot be issued.
2. **Incomplete Upper Bound Invariant:** As long as `completedRequiredItems < totalRequiredItems`, displayed progress cannot exceed `99%`. The boundary condition $199 / 200 = 99.5\%$ outputs `99%`, retaining `isCompleted = false`.
3. **Completion Gating Invariant:** Completion status (`status = 'completed'` or `isCompleted = true`) requires `totalRequiredItems > 0 && completedRequiredItems === totalRequiredItems` strictly matched against the currently published item `contentVersion`. It is never inferred solely from percentage values.
4. **Certificate Coexistence Invariant:** A learner completing Version 1 receives a Version 1 certificate. Subsequent publication of Version 2 does not alter or revoke the Version 1 certificate. Completing Version 2 issues a second certificate.
