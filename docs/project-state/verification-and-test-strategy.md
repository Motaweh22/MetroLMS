## 1. Verification Governance Model (Two-Gate Protocol)

Per the Pre-Backend Migration Remediation governance model established in [`docs/backend/pre-backend-migration-remediation-roadmap.md`](../backend/pre-backend-migration-remediation-roadmap.md) and [`docs/project-state/active-roadmap.md`](active-roadmap.md):

1. **Authoring During Remediation Phases 1–11 (Active Phases 1–3):** Every remediation work package authors or updates unit and integration test suites in `frontend/src/test/` alongside production code changes, but **defers test runner execution** until `Gate B` (`Active Phase 4`).
2. **Gate B — Consolidated Verification (`Remediation Phase 13` / `Active Phase 4`):** Once all frontend remediation and security hardening work packages (`WP-1.1` through `WP-3.4`) and API normalization work packages (`WP-4.1` through `WP-4.3`) are complete, the full verification pipeline is executed under **`WP-4.4`**:
   - `npx vitest run` (Complete unit + integration + MSW test suite — `WP-4.4` / `T-4.4.1`)
   - `npx tsc --noEmit` (TypeScript 5.7 strict typechecking — `WP-4.4` / `T-4.4.2`)
   - `npx eslint .` (Static linting & architectural boundary checks — `WP-4.4` / `T-4.4.2`)
   - `npx vite build` (Production bundle & asset integrity verification — `WP-4.4` / `T-4.4.2`)

### 6.4 Runtime Token Lifetime and Browser Page Reload Analysis (Section 6 Findings & T-1.1.1 Fail-Closed Remediation)

Inspection of the three-tier representation in [`frontend/src/core/auth/authStorage.ts`](../../frontend/src/core/auth/authStorage.ts) (`RuntimeDeveloperOriginSession`, `PersistedDeveloperOriginSnapshot`, `InertDeveloperOriginSnapshot`), the closure variable `inMemoryRuntimeDeveloperToken` ([`L354`](../../frontend/src/core/auth/authStorage.ts#L354)), `getRuntimeDeveloperTokenForRestore()` ([`L458–L468`](../../frontend/src/core/auth/authStorage.ts#L458-L468)), and the restoration and digest paths in [`frontend/src/core/auth/AuthContext.tsx`](../../frontend/src/core/auth/AuthContext.tsx) (`computeOriginSnapshotDigest` at [`L57–L141`](../../frontend/src/core/auth/AuthContext.tsx#L57-L141), `revalidateSession` Case E at [`L366–L443`](../../frontend/src/core/auth/AuthContext.tsx#L366-L443), `returnToDeveloperSession` at [`L882–L1059`](../../frontend/src/core/auth/AuthContext.tsx#L882-L1059), and `returnFromExpiredPersonaSession` at [`L1081–L1372`](../../frontend/src/core/auth/AuthContext.tsx#L1081-L1372)) yields the following findings:

1. **Exact Behavior of `authStorage.getRuntimeDeveloperTokenForRestore()`:**
   - [`getRuntimeDeveloperTokenForRestore()` (`authStorage.ts#L458-L468`)](../../frontend/src/core/auth/authStorage.ts#L458-L468) returns the volatile runtime token (`inMemoryRuntimeDeveloperToken`) when a valid, unexpired, non-inert (`snapshotState !== 'inert'`) Developer origin snapshot exists, or `null` otherwise.
   - **It does NOT itself synthesize any deterministic fallback token.**
2. **Removal of the Previous Deterministic Fallback in `AuthContext.tsx` (`T-1.1.1` Targeted Remediation):**
   - Previously, `AuthContext.tsx` constructed a deterministic fallback token (`mock_jwt_${CANONICAL_DEVELOPER_ID}_${Date.parse(origin.savedAt) || Date.now()}`) at the two restoration call sites (`returnToDeveloperSession` and `returnFromExpiredPersonaSession`) when `getRuntimeDeveloperTokenForRestore()` returned `null`, and `computeOriginSnapshotDigest()` fell back to an empty `runtimeTokenScope` (`''`).
   - **Both deterministic fallback expressions in `AuthContext.tsx` have been permanently removed**, and `computeOriginSnapshotDigest()` no longer falls back to `''`.
3. **Strict Fail-Closed Behavior When Volatile Credentials Are Unavailable:**
   - `returnToDeveloperSession()` ([`AuthContext.tsx#L914-L927`](../../frontend/src/core/auth/AuthContext.tsx#L914-L927)) and `returnFromExpiredPersonaSession()` ([`AuthContext.tsx#L1265-L1285`](../../frontend/src/core/auth/AuthContext.tsx#L1265-L1285)) obtain the runtime credential exclusively through `authStorage.getRuntimeDeveloperTokenForRestore()`.
   - When `getRuntimeDeveloperTokenForRestore()` returns `null` (such as after a true browser reload that wipes `inMemoryRuntimeDeveloperToken`, or when only persisted snapshot metadata exists in `sessionStorage`):
     - Restoration **fails closed** immediately.
     - No token is synthesized, derived, reconstructed, or substituted from `savedAt`, user IDs, persona IDs, snapshot metadata, or public constants.
     - No restored authenticated session is written to `authStorage`.
     - `AuthContext.user` is **not** set to the Developer user.
     - `computeOriginSnapshotDigest()` ([`AuthContext.tsx#L101-L115`](../../frontend/src/core/auth/AuthContext.tsx#L101-L115)) returns `null`, and `revalidateSession()` Case E ([`AuthContext.tsx#L370-L443`](../../frontend/src/core/auth/AuthContext.tsx#L370-L443)), `isSynchronouslyValid` ([`L1381-L1391`](../../frontend/src/core/auth/AuthContext.tsx#L1381-L1391)), and the digest validation effect ([`L1426-L1442`](../../frontend/src/core/auth/AuthContext.tsx#L1426-L1442)) never establish or preserve `emergencyProof` when the volatile runtime credential is unavailable.
     - The user must initiate a fresh Developer session through the legitimate login flow.
4. **Explicit `import.meta.env.DEV` Entry Boundaries & Production Asset Hygiene:**
   - `launchIsolatedTestSession()` ([`AuthContext.tsx#L698-L703`](../../frontend/src/core/auth/AuthContext.tsx#L698-L703)), `returnToDeveloperSession()` ([`AuthContext.tsx#L884-L890`](../../frontend/src/core/auth/AuthContext.tsx#L884-L890)), `returnFromExpiredPersonaSession()` ([`AuthContext.tsx#L1095-L1104`](../../frontend/src/core/auth/AuthContext.tsx#L1095-L1104)), and `computeOriginSnapshotDigest()` ([`AuthContext.tsx#L63-L65`](../../frontend/src/core/auth/AuthContext.tsx#L63-L65)) enforce explicit `if (!import.meta.env.DEV)` guards at their entry boundaries so synthetic test-persona operations fail closed in production builds before creating tokens, mutating authentication state, or writing storage.
   - In addition to the runtime `if (import.meta.env.DEV)` MSW startup guard in [`frontend/src/main.tsx#L7`](../../frontend/src/main.tsx#L7), [`frontend/vite.config.ts#L132-L149`](../../frontend/vite.config.ts#L132-L149) includes a build-only plugin (`excludeMswWorkerInBuildPlugin`, `apply: 'build'`) that removes `mockServiceWorker.js` from the production output directory (`dist/`) without affecting development (`vite`) or testing (`vitest`).
5. **Interaction with JSDOM Reload Simulation (`P5-T16-2`, `P5-T24-1`) and Future `WP-1.3` (`D-AUTH-01`):**
   - In JSDOM (`P5-T16-2` and `P5-T24-1`), `authStorage.saveDeveloperOriginSession(origin)` is called in the same process prior to mounting `<AuthProvider>`, so `inMemoryRuntimeDeveloperToken` remains populated in closure memory during the JSDOM test. In a true browser reload under the current MSW token model, volatile memory is wiped and restoration fails closed. In **`WP-1.3` (`T-1.3.1` / `T-1.3.3`)**, authentication transitions to **Django Server-Side Sessions (`D-AUTH-01`)** where session continuity across reloads is governed by `HttpOnly`, `Secure` server-side session cookies and `GET /api/auth/me` rather than client-stored tokens.
   - **Verification Status:** `T-1.1.1` remains **`IMPLEMENTED — VERIFICATION PENDING`**, and runtime verification of all 60 specifications in `isolated-role-session.test.tsx` remains deferred to **Phase 4 (`WP-4.4` / `Gate B`)**.
