## 1. Domain Overview & Mission

- **Domain Mission:** Maintain a strict decoupling boundary (`D-MEDIA-01`) between frontend/application metadata (`MediaAssetReference`, `GroupMaterialFolder`, `GroupMaterialFile`) and physical media binary storage/delivery, while preserving `API-REC-06` deferrals and `API-REC-07` `PUT` vs. `PATCH` resource semantics.
- **Domain Boundaries:**
  - *In Scope:* `D-MEDIA-01` decoupled media contract, approved initial binary upload path (`Browser -> Django Backend -> Media Storage` via `multipart/form-data` through a storage abstraction — `OWNER APPROVED`, `2026-11-13`), **Phase 1 Django-Mediated Media Delivery** (`OWNER APPROVED`, `2026-11-13` — session-authenticated Django streaming via storage abstraction with `Range`/`206`/`416` requirements), `CL-02` internal + external trainee network access (`OWNER APPROVED`, `2026-11-13`), `CL-03` short-lived signed-URL strategy (historically `OWNER APPROVED`, `2026-11-13`, clarified as **future architectural direction; implementation deferred**), Google Drive `Anyone with the link` external video policy (`OWNER APPROVED FOR GOOGLE DRIVE VIDEO SOURCES`, `2026-11-13`), entity-based storage organization design direction (`INV-DOM21-05`), initial Windows Server storage deployment direction (`INV-DOM21-06`), group material folder/file metadata lifecycle, local IndexedDB prototype isolation (`mediaStorageService.ts`), and explicit documentation of remaining deferred media decisions (`API-REC-06`).
  - *Out of Scope (Remaining Deferred under `API-REC-06`):* Implementing Signed URLs or a separate Media Delivery Service (deferred to a future phase; no Starlette, Uvicorn, ASP.NET Core, S3, MinIO, CDN, Redis, or Celery in Phase 1), physical storage provider or NAS/File Server implementation details, `CL-03` future technical details (exact TTL, signature algorithm & key management/rotation, URL scope, Range reuse, replay mitigation, delivery-server validation, post-change URL invalidation, external streaming performance/ops), malware scanning policy/engine, exact production file-size limits, chunked/resumable upload, backup/retention policies, and immutable asset replacement/deletion lifecycle — **`API-REC-06` remains `DEFERRED` until all required media Owner decisions are resolved**.
- **Core Entities:** `MediaAssetReference`, `GroupMaterialFolder`, `GroupMaterialFile` *(all persistence fields remain `PROVISIONAL — OWNER REVIEW REQUIRED`)*.

## 3. Approved vs. Current Prototype vs. Target Behavior

- **Approved Business Behavior:** `D-MEDIA-01` mandates a decoupled media contract; `ADR-004` keeps media payloads out of core transactional DB rows.
- **Current Prototype Behavior:**
  - Course media blobs (video/PDF/image) are stored locally in browser IndexedDB (`frontend/src/core/storage/mediaStorageService.ts`, `metro_lms_media_db`), strictly isolated to the local browser origin.
  - Group material endpoints (`groupHandlers.ts`, `inMemoryStore.ts`) transport JSON metadata only (`{ fileName, sizeBytes, mimeType }` -> `/dev-media/materials/...`), with no binary stream or `FormData`.
- **Implementation Gap:** No cross-device server binary upload, streaming, or delivery authorization exists in the prototype; `deleteMaterialFolder`, `moveMaterialFile`, and `updateMaterialFile` (`PATCH`) currently have `NO TEST`.
- **Target Backend Behavior (Constrained):**
  - **Approved Initial Upload (`OWNER APPROVED`, `2026-11-13`):** `Browser -> Django Backend -> Media Storage` via `multipart/form-data`. Django enforces `D-AUTH-01` session/CSRF authentication, `D-SEC-01` authorization, server-side file/MIME/size validation, safe internal storage key generation, storage-abstraction writes, SQL Server metadata persistence, and upload audit logging. Initial deployment may use dedicated space on the existing Windows Server (subject to confirmed capacity, backup, permissions, and operational safeguards) while preserving seamless migration to a dedicated Media Server without rewriting business logic or changing logical asset references.
  - **Deferred / Unresolved (`API-REC-06` remains `DEFERRED`):** Direct-to-storage upload authorization and chunked/resumable upload are deferred alternatives; exact production file-size limits (never inferred from prototype limits), physical storage engine (`MEDIA_ROOT` vs. NAS vs. object storage), malware scanning policy, CDN, network exposure (`CL-02`), and delivery authorization (`CL-03`) remain unresolved. Approval of `Browser -> Django` upload does NOT authorize Django-mediated video streaming (`ADR-004` direct client streaming remains mandatory).
  - **Target Contract Note (`API-REC-07`):** Target Django multipart upload endpoints must handle binary upload separately from `API-REC-07` `PUT` (file-reference metadata replacement) and `PATCH` (display metadata/visibility); prototype JSON-only upload handlers do not yet implement the target multipart upload contract.
- **Deferred / Provisional Notice:** All media reference columns remain **`PROVISIONAL — OWNER REVIEW REQUIRED`**.
