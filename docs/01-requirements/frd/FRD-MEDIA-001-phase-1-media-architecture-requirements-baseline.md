## 1. Executive Summary

This document consolidates and classifies all requirements, constraints, and open decisions governing MetroLMS media handling for **Phase 1** without modifying any existing Owner decisions, implementing code, or freezing Phase 5 database schemas.

Following the Owner's **Phase 1 Django-Mediated Media Delivery** decision (`2026-11-13`), not every unresolved item under `API-REC-06` blocks the Phase 1 Media API Contract. By separating **Category A (Phase 1 API Contract Blockers)** from **Category B (Phase 1 Production Readiness Requirements)** and **Category C (Future Enhancements / Deferred Scope)**, MetroLMS can finalize a minimal, stable Phase 1 API contract once the small set of Category A behavioral rules is confirmed, while deferring infrastructure sizing, operational hardening, and future Signed URL / Media Server scaling to their appropriate gates.

**Key Governance Guardrails:**
- `API-REC-06` remains **`DEFERRED`** until its remaining mandatory media Owner decisions are explicitly resolved.
- Historical `CL-03` approval (`Short-Lived Signed URL Strategy`, `2026-11-13`) is preserved as a **future** architectural direction whose implementation is **deferred**.
- Phase 5 Owner Input & Schema Review remains mandatory before any database-bound media metadata, DTOs, or SQL Server schemas are finalized.

## 2. Existing Owner-Approved Decisions (Preserved Baseline)

All of the following Owner-approved decisions remain binding and unmodified:

1. **Decoupled Media Contract (`D-MEDIA-01`):** Frontend and core Django endpoints consume logical `MediaAssetReference` descriptors (`assetId`, `url`, `mimeType`, `fileName`, `sizeBytes?`, `disposition?`) independent of physical storage paths (`system-architecture.md`, `django-sqlserver-integration-contract.md` §3).
2. **Backend & Database Stack (`D-DB-01`):** Python 3.12+ / Django 5+ / DRF + **Microsoft SQL Server** (`pyodbc` / `mssql-django`). PostgreSQL is prohibited.
3. **Authentication & Authorization (`D-AUTH-01`, `D-SEC-01`):** Django server-side `HttpOnly` / `Secure` session cookies + `X-CSRFToken`; Django independently enforces authentication, RBAC, course/group/cycle authorization, visibility, and audit logging.
4. **Initial Upload Architecture (`OWNER APPROVED`, `2026-11-13`):** `Browser -> Django Backend -> Media Storage` via `multipart/form-data`, with server-side validation, safe internal storage keys, Storage Abstraction writes, SQL Server metadata persistence, and upload audit logging. `API-REC-07` (`PUT` file-reference replacement vs. `PATCH` display metadata/visibility) remains unchanged.
5. **Phase 1 Media Delivery (`OWNER APPROVED`, `2026-11-13`):** Initial production uses **Django-mediated, session-authenticated media delivery** through the Storage Abstraction (private storage, stable asset IDs, preserving HTTP `Range`, `206 Partial Content`, `416`, repeated Range requests with authorization, and native seeking). No separate Media Delivery Service is required in Phase 1 (and no Starlette, Uvicorn, ASP.NET Core, S3, MinIO, CDN, Redis, Celery, or silent ASGI change is introduced).
6. **Network Exposure (`CL-02` — `OWNER APPROVED`, `2026-11-13`):** Platform and authorized media delivery must support both Cairo Metro's internal corporate network and external internet access (home/mobile) over HTTPS, never exposing Windows shares, SMB paths, or physical storage locations, and without approving public buckets, public binary URLs, or a CDN.
7. **Entity-Based Storage Organization (`INV-DOM21-05` — `OWNER-APPROVED DESIGN DIRECTION`, `2026-11-13`):** Logical organization by owning entity (Course, Group, User where genuine use case exists, System, Staging/Quarantine, Derivatives) using stable internal IDs, generated Asset IDs, version preservation, and shared-binary deduplication (not a frozen physical directory tree, DB schema, or retention policy).
8. **Initial Physical Storage Deployment (`INV-DOM21-06` — `OWNER APPROVED — INITIAL STORAGE DEPLOYMENT DIRECTION`, `2026-11-13`):** Dedicated media storage on the existing Windows Server hosting Django and SQL Server, separated from app source/deployment, logs/temp, and SQL Server data/transaction-log directories (illustrative `D:\MetroLMSMedia\`), accessed via Storage Abstraction to enable future migration to a separate Media Server.
9. **Future `CL-03` Signed URLs (`OWNER APPROVED`, `2026-11-13` — Implementation Deferred):** Short-Lived Signed URLs and `ADR-004` direct client streaming remain preserved as the **future** media authorization and delivery direction when traffic/performance justifies a separate delivery layer.
10. **Google Drive Video Sources (`OWNER APPROVED FOR GOOGLE DRIVE VIDEO SOURCES`, `2026-11-13`):** External Google Drive videos use `Anyone with the link` viewer sharing (reference/ID stored, never copied into MetroLMS storage; direct-link limitation applies outside MetroLMS until Drive permissions change; applies ONLY to Google Drive, never MetroLMS-owned storage; no OAuth, MetroLMS signed URLs, or proxying required).
11. **Immutable Media Assets for Published References (`INV-DOM21-07` — `OWNER APPROVED`, `2026-11-13`):** Any media asset associated with a `PublishedCourseVersion` or a sealed/closed `GroupRenewalCycle` is binary-immutable and identity-immutable (never overwritten in place; old `assetId` never reused). Replacement creates a new media asset with a new stable `assetId` while preserving the original historical asset independently in storage; existing published/sealed references continue pointing to their original asset, and `API-REC-07` `PUT`/`PATCH` metadata operations must never overwrite immutable binary content.
12. **Active / Unsealed Group Renewal Cycle Media Replacement (`INV-DOM21-08` — `OWNER APPROVED`, `2026-11-13`):** `INV-DOM21-07` immutability does NOT extend to Active / Unsealed `GroupRenewalCycle`s. Authorized replacement in an active cycle is allowed (the active cycle uses the new media, the old media is no longer the active material reference for that cycle, unrelated references are not silently modified, and sealed/closed cycles remain immutable). If the old asset is also referenced by any protected historical content (`PublishedCourseVersion` or sealed/closed `GroupRenewalCycle`), the system does not overwrite globally, creates a new `assetId`, updates only the active cycle's reference, and preserves the old asset without auto-deletion. Does NOT imply any reset of learner progress, attendance, attempts, completions, or certificates.
13. **New Asset Identity for Every Binary Replacement (`INV-DOM21-09` — `OWNER APPROVED`, `2026-11-13`):** Whenever the binary content of an existing MetroLMS media asset is replaced, the replacement must create a new media asset with a new stable `assetId`. In-place binary overwriting and `assetId` reuse are prohibited regardless of lifecycle state or reference count (published course version, sealed/closed cycle, active/unsealed cycle, single active-cycle-owned asset, draft-exclusive asset, or single/multiple references). For every approved replacement: upload & validate binary, create new media asset, assign new stable `assetId`, explicitly update the applicable authorized reference where permitted, leave other references unchanged unless separately authorized, and never overwrite the previous asset's binary. Preserves `INV-DOM21-07`, `INV-DOM21-08`, and `API-REC-07` (`PUT`/`PATCH` metadata operations do not authorize in-place binary replacement; endpoint sequence/request contracts remain proposed unless Owner-approved). Does NOT authorize deleting the old asset or resolve exact RBAC role mapping, one-step vs. two-step API workflow, failure/consistency guarantees, metadata mutability/snapshots, deletion/retention/orphan cleanup, reference counting, or learner progress/record reset rules.
14. **Draft Course Version Media Replacement (`INV-DOM21-10` — `OWNER APPROVED`, `2026-11-13`):** Authorized course administrators may replace media content associated with a Draft Course Version before publication through the authorized draft editing workflow, strictly following `INV-DOM21-09` (new `assetId`; no in-place binary overwrite, even for draft-only assets; leaves `PublishedCourseVersion`s under `INV-DOM21-07`, sealed group cycles, and unrelated active-cycle references under `INV-DOM21-08` untouched; preserves `API-REC-07` `PUT`/`PATCH` meanings; does not delete the old asset). Approves the draft replacement capability only—not a specific endpoint sequence (single multipart upload-and-repoint vs. two-step upload/create-asset-then-repoint remain `PROPOSED`) and does not invent transactional atomicity if upload + asset creation succeeds while draft reference update fails.
15. **Draft Media Replacement Authorization (`INV-DOM21-11` — `OWNER APPROVED`, `2026-11-13`):** A user may replace media associated with a Draft Course Version **only** if authorized to edit **that specific target Draft Course Version** (inherited from Draft Course Version editing authorization under `domain-05`, `D-SEC-01`, `INV-R6`, and `INV-R9`, without inventing new roles or independent permissions). General system-wide file upload permission alone does not grant permission to replace media within a Draft Course Version or repoint an existing course-content reference. Django must independently enforce authorization on the server across both operations (frontend controls/hidden UI are insufficient). Governs Draft Course Version media replacement only (not group materials, user files, or system assets) and preserves `INV-DOM21-07`–`INV-DOM21-10` and `API-REC-07`. Exact role-to-permission mapping where not already established, API mechanics, partial-failure consistency, and remaining API request/response details remain unresolved.
16. **Two-Step Media Upload & Reference Repoint Workflow (`INV-DOM21-12` — `OWNER APPROVED`, `2026-11-13`):** Media replacement (for `INV-DOM21-10` Draft Course Versions and `INV-DOM21-08` Active / Unsealed `GroupRenewalCycle`s; never modifying `INV-DOM21-07` protected historical references) is separated into two distinct operations: **Step 1 (Upload & Create Asset)** uploads the binary via Django `multipart/form-data`, authenticates/validates context authorization (`INV-DOM21-11` for drafts; existing group rules for active cycles), validates the file, creates a new asset with a new stable `assetId` (`INV-DOM21-09`), stores it via Storage Abstraction, and returns the new asset reference **without automatically modifying any course or group material reference**; **Step 2 (Repoint Target Reference)** submits a separate operation identifying the target reference + new `assetId`, independently authenticates and **revalidates** user authorization, target lifecycle state, replacement eligibility, and new `assetId` validity/eligibility, and updates only that target reference (replacement is complete **only after** Step 2 succeeds; other references remain unchanged). Preserves `API-REC-07` (`PUT`/`PATCH` metadata meanings; do not conflate binary upload, asset creation, reference repoint, and metadata update). Does NOT imply one atomic DB transaction (Scenarios A–D: if Step 1 succeeds and Step 2 fails, old reference stays unchanged, new asset is not auto-deleted, and unreferenced-asset/retry/cleanup implications belong to `B-08`). Exact endpoint paths, HTTP methods, request/response DTOs, multipart field names, status/error codes, asset lifecycle status values, idempotency-key/retry protocol, and transaction boundaries remain `PROPOSED`.
17. **Context-Specific Media Display Metadata (`INV-DOM21-13` — `OWNER APPROVED`, `2026-11-13`):** Display properties `title` and `isVisible` belong to the specific content/material usage reference (not as globally shared properties of the underlying Media Asset); shared assets retain independent `title` and `isVisible` per usage reference, and updating one reference must not modify other references or silently alter unrelated presentations. `fileName`, `mimeType`, and `sizeBytes` remain Asset-level technical metadata. Under `API-REC-07`, `PUT` retains file-reference/asset metadata replacement (including applicable technical metadata) and `PATCH` updates `title` and `isVisible` **on the applicable content/material reference** (neither authorizes in-place binary replacement).
18. **Reference Metadata Mutability Follows Content Lifecycle (`INV-DOM21-14` — `OWNER APPROVED`, `2026-11-13`):** Mutability of reference-level `title` and `isVisible` (`INV-DOM21-13`) is governed independently by the lifecycle state of the specific target content/material reference: **mutable** in **Draft Course Versions** (with existing authorization) and **Active / Unsealed Group Renewal Cycles** (with existing group-level authorization), and **historically immutable** in **Published Course Versions** and **Sealed / Closed Group Renewal Cycles** (in-place modification prohibited; future cycles/versions manage their own references independently). Asset-level technical metadata (`fileName`, `mimeType`, `sizeBytes`) remains separate and is not governed by these reference-level rules. Under `API-REC-07`, `PATCH` permission to modify `title`/`isVisible` is constrained accordingly (Draft & Active/Unsealed permitted; Published & Sealed/Closed prohibited in-place; no invented paths, methods, DTOs, or error codes; neither `PUT` nor `PATCH` authorizes in-place binary replacement). Preserves `INV-DOM21-07`–`INV-DOM21-13`.
19. **Immediate Visibility Enforcement for Active Group Renewal Cycles (`INV-DOM21-15` — `OWNER APPROVED`, `2026-11-13`):** When an authorized user changes reference-level `isVisible` of a material reference in an Active / Unsealed `GroupRenewalCycle` from `true` to `false`, the change takes effect **immediately** after successful persistence: the material becomes unavailable to **all trainees** in the affected cycle (not only the initiating admin), trainees must no longer be allowed to initiate access on subsequent access decisions (independently enforced by Django), the material reference and underlying Media Asset are retained, all learner educational records (progress, lesson completions, attendance, quiz/assessment attempts, completed-course history, and certificates) are preserved, and unrelated references to the same asset across other groups, courses, or lessons remain unaffected (`INV-DOM21-13`). Preserves `INV-DOM21-07`–`INV-DOM21-14` and `API-REC-07`. Does NOT decide `isVisible: false -> true` restoration behavior, already-open playback sessions / in-flight HTTP `Range` requests / previously issued media responses (do not invent immediate stream termination or session revocation), automatic trainee notifications, progress recalculation, deadline/schedule changes, exact API/caching mechanisms, or additional `B-13` audit/ops requirements.
20. **Immutable Asset-Level Technical Metadata (`INV-DOM21-16` — `OWNER APPROVED`, `2026-11-13`) & `API-REC-07` Reconciliation:** Asset-level technical metadata fields `fileName`, `mimeType`, and `sizeBytes` (`INV-DOM21-13`) belong to the underlying Media Asset and become **immutable immediately after that asset is successfully created**, established from the uploaded file and its server-validated properties (client-declared MIME type or size is never authoritative without server-side validation; `B-01`/`B-02` remain production-readiness requirements without selecting a specific validation library or algorithm). Across all lifecycle states and reference counts (no exceptions): these fields must not be modified in place, API operations must not allow manual overwriting, display-metadata updates must not change them, and binary replacement must create a new Media Asset with a new stable `assetId` (`INV-DOM21-09`, `INV-DOM21-12` Step 1 + Step 2) leaving the previous asset and its technical metadata unchanged. **Narrow `API-REC-07` Reconciliation:** Preserves `API-REC-07` historical record; `INV-DOM21-16` supersedes any conflicting interpretation of `API-REC-07` **only** regarding post-creation modification of `fileName`, `mimeType`, and `sizeBytes` (`PUT` must not mutate these immutable Asset-level fields after creation; `API-REC-07` requires reconciliation / a narrowly scoped amendment during API Contract review to establish exact revised `PUT` semantics, endpoint paths, DTOs, and resource-targeting behavior without inventing a new `PUT` meaning). Preserves `INV-DOM21-07`–`INV-DOM21-15`.
21. **Separate Content Reference Removal from Media Asset Deletion (`INV-DOM21-17` — `OWNER APPROVED`, `2026-11-13`):** **Content Reference Removal** (targeting a specific course, lesson, or group material usage reference) and **Media Asset Deletion** (targeting the underlying Media Asset) are **separate domain operations** and must not be conflated with binary replacement (`INV-DOM21-09`), repointing (`INV-DOM21-12`), display-metadata updates (`INV-DOM21-13`), or Asset-level technical metadata mutation (`INV-DOM21-16`). Removing a content/material reference affects only that target reference (enforcing target authorization and lifecycle restrictions), must not automatically delete the underlying Media Asset, must not modify/delete other references to the same asset, and must not alter the underlying binary or its technical metadata. An underlying Media Asset must **not** be physically deleted while **any** content/material reference still depends on it across **all** lifecycle states (Draft Course Versions, Published Course Versions under `INV-DOM21-07`, Active / Unsealed Group Renewal Cycles, Sealed / Closed Group Renewal Cycles under `INV-DOM21-07`, or any other usage), without ignoring inactive/historical references, cascade-deleting from an individual reference removal, or inferring immediate physical deletion eligibility when the last active reference is removed. Preserves `API-REC-07` (`PUT`/`PATCH` do not perform Content Reference Removal or Media Asset Deletion) and `INV-DOM21-07`–`INV-DOM21-16`. Reference removal semantics (soft deletion vs. logical detachment vs. physical deletion *(logical detachment subsequently resolved by `INV-DOM21-18`)*), exact reference-removal eligibility/authorization rules in Drafts and Active / Unsealed cycles, exact deletion API paths/methods/DTOs/status codes, asset soft-deletion/archival/permanent deletion, zero-reference retention rules, retention periods, physical storage cleanup/orphan handling, dependency-counting mechanism, audit requirements, and concurrency/transaction boundaries remain unresolved.
22. **Logical Content Reference Detachment (`INV-DOM21-18` — `OWNER APPROVED`, `2026-11-13`):** Removing a media Content Reference from a course, lesson, or group material must use **Logical Detachment** rather than physically deleting the reference record. The operation must: (1) detach the specific Content Reference from the currently active course, lesson, or group material presentation; (2) stop presenting that reference as an active material in the affected context; (3) prevent trainees from initiating new access to the material through that removed reference; (4) preserve the historical reference record and its removal history; (5) preserve the underlying Media Asset and its binary; and (6) leave unrelated references to the same Media Asset unchanged. Logical detachment must not automatically delete the underlying Media Asset/binary, modify Asset-level technical metadata (`fileName`, `mimeType`, `sizeBytes`), delete other references, reset learner progress, delete lesson completion history, delete attendance records, reset assessment attempts, delete completed-course history, or revoke/delete issued certificates. Preserves all lifecycle restrictions (`INV-DOM21-07` historical immutability), server-side authorization, `INV-DOM21-07`–`INV-DOM21-17`, and `API-REC-07` (`PUT`/`PATCH` are not approved reference-removal endpoints). Do not infer that retaining a historical record keeps the detached reference available to trainees, that logical detachment authorizes or triggers physical asset deletion eligibility, or that it terminates already-open video sessions or in-flight HTTP `Range` requests. Exact eligibility/authorization by lifecycle state *(context-specific authorization rule subsequently established by `INV-DOM21-19`)*, exact logical state representation (do not invent `detached`/`removed`/`archived`), additional audit metadata (actor, timestamp, reason), restoration/reattachment & identity reuse, exact removal API contracts, already-open playback sessions / in-flight `Range` requests, Asset soft-deletion/archival/permanent deletion, zero-reference retention, retention periods, dependency detection, physical cleanup/orphan handling, and concurrency boundaries remain unresolved.
23. **Context-Specific Content Reference Removal Authorization (`INV-DOM21-19` — `OWNER APPROVED`, `2026-11-13`):** A user may logically detach (`INV-DOM21-18`) a media Content Reference **only** when authorized to manage content within **the specific target context** containing that reference, reusing existing context-specific content-management permissions where they already cover the operation (without inventing new roles or unnecessary independent permissions): **(a) Draft Course Versions:** permitted only if authorized to edit that specific target Draft Course Version (`INV-DOM21-11`, `domain-05`, `D-SEC-01`, `INV-R6`, `INV-R9`; general upload permission or permission on another course/draft is insufficient); **(b) Active / Unsealed Group Renewal Cycles:** permitted only if authorized to manage content/materials of that specific target group or cycle under existing group-level authorization (`D-SEC-01`, `INV-R6`, `INV-R7`, `INV-R9`, `GroupAssistantAssignment` `materials.delete_files` / `materials.manage_folders` in `authorization-and-permissions-design.md`; general upload permission, broad admin status without target-group authority, or permission on another group is insufficient); and **(c) Published Course Versions & Sealed / Closed Group Renewal Cycles:** Logical Detachment must not modify protected historical references (`INV-DOM21-07`; no exception for administrators or other privileged roles). Django must independently verify on every reference-removal request: authenticated user's current authorization, exact target Content Reference, owning context, target lifecycle state, and Logical Detachment eligibility (frontend controls or prior upload/edit/replacement checks are never sufficient). Preserves `INV-DOM21-07`–`INV-DOM21-18` and `API-REC-07` (`PUT`/`PATCH` are not approved Logical Detachment endpoints; does not define restoration/reattachment or authorize physical asset deletion). Exact role-to-permission mapping where not already documented (including whether `assistant_admin` group-material detachment requires `INV-R9` approval or whether `supervisor` has material-detachment authority), any authorization gaps in existing group management permissions, exact removal API paths/methods/DTOs/status & error codes, and additional audit requirements remain unresolved.
24. **Draft Media Reference Management Through `courses.edit_curriculum` (`INV-DOM21-20` — `OWNER APPROVED`, `2026-11-13`):** Existing `courses.edit_curriculum` is the approved authorization basis for managing media Content References within an eligible target **Draft Course Version** (without inventing new `PermissionKey`s), covering: (1) adding a media Content Reference, (2) logically detaching an existing reference (`INV-DOM21-18`), (3) repointing a reference to a newly created Media Asset (`INV-DOM21-12` Step 2), and (4) updating reference-level `title` and `isVisible` (`INV-DOM21-13`, `INV-DOM21-14`). `courses.upload_lectures` authorizes Step 1 binary upload & Asset creation only and **alone never authorizes** attaching, detaching, or repointing a Draft media reference; `courses.delete_lectures` remains distinct for deleting entire lecture/quiz items; `courses.edit_metadata` remains course-level metadata. Evaluated via `UserPermissionOverride`, `ROLE_CAPABILITY_CEILINGS`, `authorId === actor.id` ownership (`lecturer` requires effective grant + ownership), `INV-R1`–`INV-R8`, Visual Role Preview barriers (`developer`), and `user`/`trainee` exclusion; `assistant_admin` Draft scope under `INV-R7` remains **unresolved**. Applies **only** to Draft Course Versions (never Published, Sealed/Closed, Active/Unsealed Group Renewal Cycles, group materials, user media, or system media); Django independently verifies target-Draft authorization on the server. API paths, HTTP methods, DTOs, status codes, idempotency, and transaction boundaries remain unresolved.
25. **Dedicated Group Media Reference Management Permission (`materials.manage_references` — `INV-DOM21-21` — `OWNER APPROVED`, `2026-11-13`):** Introduces `materials.manage_references` as a distinct permission governing media Content References within an eligible, specifically assigned **Active / Unsealed Group Renewal Cycle**, covering: (1) adding a media Content Reference, (2) logically detaching an existing reference (`INV-DOM21-18`), (3) repointing a reference to a newly created Media Asset (`INV-DOM21-12` Step 2), and (4) updating reference-level `title` and `isVisible` (`INV-DOM21-13`–`15`). `materials.upload_files` authorizes Step 1 supplementary group binary upload & Asset creation only (never attaching, detaching, repointing, or changing `title`/`isVisible`); `materials.delete_files` retains supplementary file deletion (never reinterpreted as `INV-DOM21-18` Logical Detachment or physical Asset deletion); `materials.manage_folders` remains folder structure only; `courses.edit_curriculum` remains Draft Course Versions only (`INV-DOM21-20`). Applies **only** to Active / Unsealed Group Renewal Cycles (never Drafts, Published/Sealed under `INV-DOM21-07`, user/system media, or Asset deletion under `INV-DOM21-17`); Django independently verifies current effective permission and target group/reference scope on the server (cross-group grants prohibited). Default role grants (`developer`, `super_admin`, `admin`, `assistant_admin`, `lecturer`, `supervisorIds`), exact individual grantability & capability-ceiling placement, `assistant_admin` `INV-R9`/`DelegatedAuthority` applicability (`INV-R7` assigned-group writes still apply), `supervisorIds` non-mutation boundary, and API contracts remain unresolved (do not invent default grants).

## 4. Deep-Dive Analysis

### 4.1 Upload Contract vs. Upload Limits
- **API Stability via Configurable Limits:** Exact numeric file-size caps (e.g., MB per type) do **not** need to be hardcoded in the Phase 1 API Contract. Keeping limits configurable on the Django server preserves API stability as storage capacity evolves.
- **Client Contract Needs:** When an upload exceeds the server-configured limit or violates MIME/type rules, Django must return a deterministic canonical error (`413 Payload Too Large` or `422 Unprocessable Entity` using `django-sqlserver-integration-contract.md` §2.4 `{ status: "ERROR", code, message, fieldErrors }`) with a clear Arabic user message so the frontend can surface the rejection cleanly.

### 4.2 Streaming & Django Capacity (Phase 1)
- **Approved Requirements:** Django authenticates (`D-AUTH-01`), authorizes (`D-SEC-01`), reads via Storage Abstraction, and streams with `Range`, `206`, `416`, and native seeking.
- **Deployment & Performance Realities:** Serving video bytes through Django WSGI workers increases worker occupancy and bandwidth pressure under concurrent playback. Neither ASGI nor a separate streaming service is approved for Phase 1. Therefore, **representative concurrent-playback workload testing (`B-09`, `B-10`) is mandatory before production sign-off**, and performance monitoring / `CL-03` migration criteria remain open for Owner/ops definition.

### 4.3 Media Replacement & Deletion Lifecycle
- **Approved Foundations (`INV-DOM21-07`–`INV-DOM21-19` — `OWNER APPROVED`, `2026-11-13`):** Assets referenced by a `PublishedCourseVersion` or sealed/closed `GroupRenewalCycle` are binary-immutable (`INV-DOM21-07`). Active / Unsealed `GroupRenewalCycle` media is replaceable (`INV-DOM21-08`), and **Draft Course Version** media is replaceable before publication (`INV-DOM21-10`). Under `INV-DOM21-09`, **every** binary replacement across all lifecycle states and reference counts creates a new media asset with a new stable `assetId`. Under `INV-DOM21-11`, draft media replacement requires authorization to edit the specific target Draft Course Version. Under `INV-DOM21-12`, replacement uses the **Two-Step Upload & Reference Repoint workflow**. Under `INV-DOM21-13`, display properties `title` and `isVisible` belong to the specific content/material reference (`fileName`, `mimeType`, `sizeBytes` remain Asset-level technical metadata). Under `INV-DOM21-14`, reference-level `title` and `isVisible` mutability follows the target reference's lifecycle state (**mutable** in Draft Course Versions & Active / Unsealed Group Renewal Cycles; **historically immutable** in Published Course Versions & Sealed / Closed Group Renewal Cycles; `API-REC-07` `PATCH` constrained accordingly). Under `INV-DOM21-15`, changing `isVisible` from `true` to `false` in an Active / Unsealed `GroupRenewalCycle` takes effect **immediately** after successful persistence for all trainees in that cycle (denying new access initiation while retaining the asset/reference, preserving all learner progress/attendance/attempts/completions/certificates, and isolating unrelated references). Under `INV-DOM21-16`, Asset-level technical metadata (`fileName`, `mimeType`, `sizeBytes`) is **immutable immediately after asset creation** (established from server-validated uploaded binary properties; never mutated in place across any lifecycle state or reference count; replacement creates a new `assetId` with its own technical metadata, narrowly superseding `API-REC-07` only regarding post-creation mutation of those three fields). Under `INV-DOM21-17`–`INV-DOM21-19`, **Content Reference Removal** and **Media Asset Deletion** are separate domain operations; Content Reference Removal uses **Logical Detachment** rather than physical deletion of the reference record (detaching the specific target reference from active presentation and preventing new trainee access while preserving its historical record, removal history, learner educational records, the underlying Media Asset/binary, technical metadata, and all other references); an underlying Media Asset must **not** be physically deleted while **any** reference depends on it across all lifecycle states; and Logical Detachment requires context-specific content-management authorization on the exact target reference/context (Draft Course Version editing permission for Drafts; target group/cycle material-management permission for Active / Unsealed cycles; prohibited on Published & Sealed / Closed historical references; independently enforced by Django on the server, reusing existing permissions where they already cover the operation). None of these decisions implies any reset of learner progress, attendance, attempts, completions, or certificates.
- **API Contract Blockers & Consistency Scenarios (`A-03a`–`A-03c`, Pending Owner Input):** The two-step workflow is not one atomic DB transaction (`INV-DOM21-12` Scenarios A–D). Before freezing the Phase 1 API contract, the Owner/architects must clarify: (`A-03a`) exact endpoint paths & HTTP methods, multipart & reference-update DTOs, exact role-to-permission mappings where not already established, partial-failure consistency guarantees, retry & idempotency-key behavior, asset lifecycle status values, and status/error codes; (`A-03b`) exact revised `API-REC-07` `PUT` semantics (narrowly scoped amendment without inventing a new `PUT` meaning), `API-REC-07` endpoint paths, request/response DTOs, & resource-targeting semantics, any remaining historical snapshot requirements not already resolved (& metadata copying across versions/cycles), `isVisible: false -> true` restoration behavior, already-open playback sessions / in-flight HTTP `Range` requests / previously issued media responses, and technical enforcement & caching implications; and (`A-03c`) remaining Content Reference Removal & Media Asset Deletion semantics (exact existing role-to-permission mapping where not documented & any authorization gaps in existing course/group management permissions, exact logical state representation & audit fields, restoration/reattachment & identity reuse, exact removal/deletion API paths/methods/DTOs/status codes, Asset soft deletion vs. archival vs. later permanent deletion, zero-reference retention & deletion eligibility, and concurrency safety between reference creation and deletion).
- **Operational Policy (Category B `B-01` / `B-02` / `B-07` / `B-08` / `B-13`, Non-API-Blocker):** Server-side MIME/magic-byte/size validation enforcement (`B-01`/`B-02`, establishing Asset-level technical metadata without selecting a specific validation library), permanent deletion eligibility, retention periods, reference counting / usage tracking, physical orphan cleanup schedules (including unreferenced assets left by Step 1 when Step 2 fails), and additional audit or operational requirements for active-cycle metadata/visibility changes do not block the Phase 1 API contract and are deferred to pre-production / audit readiness.

### 4.4 Security & Authorization Verification
- **Prohibited Vectors:** Private Windows storage (`INV-DOM21-06`), UUID-based internal storage keys (`INV-DOM21-05`), and Django-mediated endpoints prevent public storage access, predictable unauthenticated binary URLs, exposed SMB/filesystem paths, and direct-file bypasses.
- **Per-Request & Range Re-Evaluation:** Because Phase 1 uses Django session cookies (`D-AUTH-01`) on every media request, Django **re-evaluates authentication and authorization on every applicable media request, including repeated HTTP `Range` requests**—ensuring immediate revocation upon logout, group removal (`D-07`), group archival (`D-GRP-07`), or post-deadline expiry (`WP-2.4`). *(Google Drive `Anyone with the link` embeds remain governed by their separate external-provider policy.)*

3. **`UserPermissionOverride` (`granted` / `revoked`):** Evaluated **before** `ROLE_DEFAULT_CAPABILITIES` (`policy.ts` lines 1344–1366). `revoked` denies even if present in `ROLE_DEFAULT_CAPABILITIES`; `granted` allows if within `ROLE_CAPABILITY_CEILINGS` without changing the user's canonical role. Does **not** bypass `GROUP_SCOPED_CAPABILITIES` or `INV-R9`.
4. **`ROLE_DEFAULT_CAPABILITIES`:** Baseline role capabilities when no override exists.
5. **Contextual & Resource Scope (`INV-R7`, Ownership, Assignments, Lifecycle):** Course ownership (`authorId === actor.id` for `lecturer`), `GROUP_SCOPED_CAPABILITIES` (`INV-R7` for `assistant_admin`; `GroupAssistantAssignment` / `primaryInstructorId` / `supervisorIds` in `policy.ts` lines 1388–1458), and target lifecycle state (`INV-DOM21-07`, `INV-DOM21-19`).
6. **Approval Gate (`INV-R9`, `INV-R10`, `domain-18`, `policy.ts` lines 1461–1473):** For `assistant_admin`, all state-changing capabilities outside `isReadOnlyCapability` / `isDirectMetaCapability` default to `requires_approval` (`HTTP 202 Accepted` -> `PendingApprovalRequest`) unless an active `DelegatedAuthority` bypass covers that exact capability (`INV-DOM18-02`). `admin` / `super_admin` approve with `INV-R10` execution-time re-validation.
